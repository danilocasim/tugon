# Munti Report MVP — Coolify operations and release gates

This runbook records the synthetic staging setup and separates it from pilot release gates. See [architecture](./ARCHITECTURE.md) and [phase gates](./TODO.md). Do not create paid resources, use real data or send real messages without separate approval.

## Hosting and environment boundaries

| Component | MVP deployment | Boundary |
| --- | --- | --- |
| Next.js | Coolify Dockerfile application, one standalone Next runtime behind Coolify's HTTPS proxy. Multi-stage non-root build; include `public/` and `.next/static`. | Public app hostname. Separate liveness and readiness; only public assets are cacheable. Build from `apps/web/`, not the prototype. |
| Supabase | Separate Coolify Docker Compose service pinned to a known upstream self-hosted release; reuse the Coolify template only if it matches the pinned deployment contract. Persist Postgres and private Storage independently of app deploys. | Auth, REST and Storage stay behind the app on the private network. Expose only the restricted WebSocket edge for browser Realtime. Keep the DB, pooler, Studio and management endpoints off public ingress. |
| Staging | Separate app hostname, Supabase stack, networks/volumes, API signing keys and provider configuration. Use a separate host if needed for capacity or stronger isolation. | Synthetic data only; restrict staging access and live outbound recipients. A preview or staging app never points to production. |
| Scheduled work | Coolify executes bounded delivery/retention tasks in the app container using an internal-only authenticated job entry point. Lease work in Postgres; never trigger side effects from an ordinary page hit. | No public scheduler control or worker keys in browser bundles. Jobs have heartbeat, time budget, per-channel send controls and alerts. |

Plan disk, memory and CPU before colocating Supabase, app, and Coolify builds. Use [Supabase's sizing guidance](https://supabase.com/docs/guides/self-hosting/docker#system-requirements), then measure headroom with pilot load and a staging restore; self-hosting on one VPS is not high availability. Keep runtime secrets in Coolify. Use distinct sender/provider credentials or safely scoped equivalents per environment. Publishable Supabase key and public API URL may reach the browser; the service/secret key, DB connection, SMTP credentials, SMS keys, and hook/worker secrets must not. Remember `NEXT_PUBLIC_*` is inlined at build time: rebuild per target public config or deliberately serve public config at runtime. Keep secret files out of Docker contexts and image layers, redact logs, and check bundle/artifact scanning in CI.

## Auth and messaging readiness

1. Verify staging HTTPS, app `SITE_URL`, Auth `API_EXTERNAL_URL`, and exact callback/redirect allowlists against the pinned release. Verify that public ingress denies Auth, REST, Storage and Studio; enforce origin and upgrade checks on the Realtime edge, and rate limits at Auth.
2. Wire the pinned GoTrue `GOTRUE_SMTP_*` variables from Coolify secrets to Resend; SMTP credentials do not go in Next's public environment. Use a verified sender domain; verify SPF/DKIM and set a DPO/owner-approved DMARC policy. Confirm TLS and provider egress from the actual Auth container; do not assume the hosting account permits SMTP. Verify email OTP, invitation, password recovery, mailbox change and redirects on approved recipients. Stage an Auth-only SMTP connectivity failure; UI must not say the email arrived when the provider rejected it.
3. For tanod OTP, prove the pinned GoTrue `GOTRUE_HOOK_SEND_SMS_*` mapping and signed HTTP delivery before relying on it; the upstream example uses `..._SECRETS` for the signing configuration. Semaphore's OTP API accepts the Auth-generated code via `code`; prove that the intended code, including leading zeroes, arrives before marking the integration ready. Use separately approved sender name, credits, thresholds, endpoints and test numbers. No fixed OTPs on production. Keep the auth path separate from `/messages` for ordinary SMS; do not store OTP payloads.
4. Dispatch and status delivery test matrix: consent at enqueue/send, offboarding, wrong/invalid or unverifiable recipient, provider outage/429, timeouts, duplicate events, process interruption, accepted versus network-confirmed delivery and alerts for unknown outcomes. Monitor spend and blocked sends; keep in-app status correct even when notifications are paused. Validate Philippine carrier delivery with approved pilot phones only.

### Staging candidate and jobs

- `Munti Report Web Staging` uses `https://muntireport.46.225.143.160.sslip.io`. Auto-deploy is disabled; pin an approved app commit explicitly. Set Coolify's healthcheck type to `cmd` and the command to `node /app/healthcheck.mjs`. This checks the private database through `/api/health/ready` without adding `curl` or `wget` to the image.
- Render the staging bundle with `node ops/coolify/build-synthetic-supabase.mjs https://muntireport.46.225.143.160.sslip.io tugon-staging <app-commit>`. It uses the immutable [Supabase revision `76883d4`](https://github.com/supabase/supabase/tree/76883d49435524645397b9f7a0048d92f69b8330/docker) (GoTrue `v2.197.0`) and the app commit's migrations and Auth templates. Keep the existing volumes, `PULONG_*` runtime keys and the private `SUPABASE_URL=http://pulong-supabase-gateway:8000`; these internal identifiers are unrelated to the public hostname. Never add a host port or public URL to the private gateway, PostgreSQL, Mailpit, or Storage.
- Assign only `edge-realtime` the domain `https://muntireport-realtime.46.225.143.160.sslip.io`, targeting container port `8080`; use it as the app's `SUPABASE_PUBLIC_URL`. Set `TUGON_ORIGIN` to the new app URL. The edge permits only `/realtime/v1/websocket` with the app origin and a WebSocket upgrade. Public signup stays off. Keep app delivery, phone auth, retention, and evidence GC off in staging.
- In default Mailpit mode only, the private `storage` container mounts [the resident Auth smoke](../../ops/coolify/smoke-synthetic-auth.mjs). Run it from a disabled/manual Coolify task: `node /opt/pulong/smoke-synthetic-auth.mjs https://muntireport.46.225.143.160.sslip.io`. It uses a disposable `example.test` address, verifies OTP replay denial, SSR refresh and release flags, and does not send real messages. Browser sessions on the former public hostname do not transfer to the new origin.
- The Coolify `v4.7.6` one-click Supabase template uses GoTrue `v2.186.0` and references generated public domains. Use the pinned upstream release and keep the unfiltered gateway private. Keep `sslip.io` for web routing; sending to residents on other addresses requires a separately owned and verified Resend sender domain.
- Serve the [versioned Auth templates](../../ops/supabase/templates/) over an operator-owned HTTPS endpoint accessible to Auth; set `TUGON_MAIL_TEMPLATES_BASE` without a trailing slash. Verify the six-digit template renders, Email Autoconfirm is off, and Resend link tracking is disabled for invitation/reset mail. Set `RESEND_SMTP_KEY` and `RESEND_SMTP_FROM` only on the Auth stack. `RESEND_API_KEY` and `RESEND_FROM` on the application are for opt-in status mail, not email verification.
- Set `TUGON_AUTH_SMS_ENABLED=on` only after staging proves the signed GoTrue hook, matching live test roster and Semaphore `/otp` support. The GoTrue hook URI must point to the authorized app `/api/auth/send-sms`. Ordinary notification delivery independently requires `TUGON_LIVE_DELIVERY=on` plus `TUGON_EMAIL_DELIVERY=on` and/or `TUGON_SMS_DELIVERY=on`. Rejected or ambiguously interrupted requests are not blindly retried. Alert on confirmed rejection, growing queue age and unknown outcomes.
- The OTP hook persists only a hash of the signed webhook ID and timing/acceptance metadata. It acknowledges a confirmed replay without sending again. An interrupted attempt with no recorded provider acceptance is not treated as success; let the officer request a fresh code through GoTrue.
- Schedule `POST /api/jobs/delivery` from inside the app container every minute, and `POST /api/jobs/retention` on a separate schedule. Example Coolify task command: `node -e 'fetch(\"http://127.0.0.1:3000/api/jobs/delivery\",{method:\"POST\",headers:{Authorization:\"Bearer \"+process.env.TUGON_JOBS_SECRET},signal:AbortSignal.timeout(25000)}).then(async r=>{if(!r.ok)process.exitCode=1;else console.log(await r.text())},()=>{process.exitCode=1})'`. Use a separately generated `TUGON_JOBS_SECRET`, and deny `/api/jobs/*` at public ingress.
- Factor recovery: an invited account enrolls a factor after password sign-in; a staff account with a verified factor must present it when resetting the password by email. A lost device requires independently verified administrator offboarding/re-enrollment under the approved staff recovery procedure. Do not bypass MFA or use recovery links as a desk login.

### One-inbox Resend verification

1. Keep the existing [verified Resend sender domain](https://resend.com/domains) and its scoped **Sending access** key during the website rename. The `sslip.io` app hostname is not an email sending domain. Keep `PULONG_RESEND_SMTP_KEY` and `PULONG_RESEND_TEST_EMAIL` directly in the staging Supabase service environment in Coolify, not in the web app, Git, or chat.
2. Append `--resend-test` to the render command above. GoTrue uses [`smtp.resend.com:587`](https://resend.com/docs/send-with-smtp) (staging verified STARTTLS; port 465 times out). Only Auth receives the key. Do not run the Mailpit smoke in Resend mode.
3. To enroll the approved inbox, run `node /opt/pulong/provision-resend-test-resident.mjs` as a disabled/manual task in `storage`. It provisions the account without sending mail or granting a role. The account survives hostname changes; the task does not change existing users.
4. From the new hostname, request one code for the approved inbox, check [Resend activity](https://resend.com/emails), and redeem it in the browser to confirm the selected report category is preserved. To roll back SMTP, render the same revision without `--resend-test`; no database rollback is needed.

### Enable protected resident enrollment on a production stack

- Keep SSLIP staging invite-only. To reproduce a recipient-specific issue there, provision only the approved test address rather than relaxing signup, and record provider delivery separately from code redemption.
- Before opening enrollment, complete the [pilot approvals](#pilot-approvals-and-run-checklist) and verify an off-host restore. Use a separate production app and Supabase stack, the approved HTTPS `TUGON_ORIGIN`, a verified transactional sender, and a [Cloudflare Turnstile Managed widget](https://developers.cloudflare.com/turnstile/get-started/) restricted to the exact production hostname. Do not use testing keys in production.
- Set `TUGON_TURNSTILE_SITE_KEY` and `TUGON_TURNSTILE_SECRET_KEY` in the app's Coolify runtime configuration. After validating both, set `TUGON_RESIDENT_PUBLIC_SIGNUP=on` in the app and `TUGON_GOTRUE_DISABLE_SIGNUP=false` in the **private** production Auth stack. The app verifies Turnstile hostname and action before allowing GoTrue to send an OTP or create an account. Never expose the GoTrue gateway publicly (including auth-only ingress), or requests could bypass the app's challenge. Browser Realtime must use a separately restricted WebSocket edge.
- Missing or invalid enrollment settings block code requests, not app readiness. Check `/api/health/ready` and an actual sign-in after configuration changes; HTTP 200 alone does not verify the signup path.
- Test a fresh inbox, a returning resident, a failed/missing challenge, an immediate resend, an expired/replayed OTP, and access denial before consent. Confirm the browser returns to the originally selected report category. Monitor GoTrue/Resend sending limits and bounces; never log the address, OTP, Turnstile token, or secret. If verification fails, suspend enrollment with `TUGON_RESIDENT_PUBLIC_SIGNUP=off` and `TUGON_GOTRUE_DISABLE_SIGNUP=true`; existing approved email accounts remain usable in invite-only mode.

## Migrations, backup and recovery

- One migration owner. Run versioned migrations from an authorized runner on the private network using a reviewed migration connection and the pinned CLI, not the runtime key or a hosted Supabase project link. Rehearse the planned change and SQL policy tests on disposable data first. Promote the same versioned changes, with an explicit production gate; avoid Studio-only schema changes.
- Use expand/contract changes while app images overlap: additive schema → new code → backfill or verify → removal in a later approved release. Readiness checks verified schema/dependency availability and fails when normal traffic cannot succeed. Provider mail/SMS failures alert independently and do not block ordinary app readiness.
- Back up **both** PostgreSQL (including Auth, grants, policy, and migration history) and private Storage object bytes on an aligned schedule to encrypted off-host storage. Record how to reconstruct configuration, signing keys, template version and object-store secrets via approved secret storage, not in logs or source. A database dump provides Storage metadata, not the files. Proposed pilot objectives: at most 24 hours data loss (RPO) and 4 hours recovery (RTO); measure and obtain owner approval rather than claiming them.
- Restore into a new restricted environment with outbound delivery and public access disabled. Check role gates, login, reference lookups, photos/object consistency and job state. Reconcile erasure/hold records and completed sends before any recovered stack can accept traffic. If a backup reintroduces previously erased data, keep it inaccessible and reapply the approved erasure rules before release. Keep retention periods/restore windows consistent with DPO policy.
- In the local synthetic drill, stop the source writers before archiving PostgreSQL data, its configuration volume, and Storage bytes. Restore the authenticated-encrypted archives into fresh empty volumes **before** first container start, using the same pinned images. Docker can populate an empty configuration volume on container creation; the rehearsal rejected it rather than overwriting it. The local timings are not pilot recovery objectives or proof of an off-host backup.
- Retention preview in Administration is read-only. For approved erasures use [the audited operator script](../../ops/supabase/approve-erasure.sql) with the request and approving administrator UUIDs. Keep `civic_settings.retention_enabled`, `TUGON_RETENTION_JOBS` and `TUGON_EVIDENCE_GC` off until the DPO approves enforcement and the restricted restore rehearsal. Prepare erasure and revoke sessions before deleting Auth; the worker waits for the corresponding Storage removal to be confirmed. Keep an off-host erasure reconciliation ledger and keep restored stacks private until reconciliation is verified.

## Pilot approvals and run checklist

| Owner | Evidence required before public pilot |
| --- | --- |
| Barangay/product owner | Approved barangay identity, contact/hours, areas and service scope; module/locale/phone UAT and acceptance of deviations from prototype. Named staff cohort and support channel. |
| Lupon secretary/reviewer | Signed approval of eligibility, deadline handling, document instructions/forms and legal-hold rules before accepting live Lupon cases. Prototype timing and templates are not legal authority. |
| DPO | Reviewed privacy notice, lawful bases/consent, vendor and hosting/data-location decisions, access/retention/erasure/backup rules under RA 10173, emergency disclosures and breach response procedure. |
| Operations owner | Written provider approval/sender readiness, cost and capacity budget, observability owner, staging restore results, rollback drill and authorization to release to the real domain. |

1. **Before release:** Record immutable app image and Supabase versions; confirm staged approvals, migration compatibility, readiness, backup age, access tests, provider policies, and synthetic smoke. Alerts cover authentication failures, requests and latency, restart/DB health, disk/pool pressure, backup age, job age/error rate and messaging spend. Logs exclude secrets, OTPs, personal report text, exact coordinates, images and recipient addresses/numbers.
2. **Release:** Apply only the reviewed compatible migrations, deploy with a readiness check through the Coolify Dockerfile application, and run authenticated smoke with approved users. Do not assume Compose rolling updates or zero downtime. Open access to the named pilot cohort and expand only after observed stability.
3. **Hold/rollback:** Hold for cross-role access issues, missing evidence, data integrity errors, failed readiness or failed core flows. Pause external deliveries or implicated module if needed; revert to the last compatible app image rather than destructively rolling down the database. If compatibility is uncertain, freeze writes and preserve evidence; restore separately under explicit approval. Recheck readiness, negative access, core flows and queue state before resuming.
